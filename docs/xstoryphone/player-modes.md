# プレイヤー進行の保存モード

XStoryPhoneは、共通の会話・検索・hookとUIを3種類のプレイヤーモードで実行できます。`project_constants` シートの `player.mode` に `server`、`browser`、`static` を指定します。省略時は `server` です。生成後の内部設定名は `playerMode` です。

|  | `server` | `browser` | `static` |
|---|---|---|---|
| 主な用途 | 人数を絞った有料体験 | 不特定多数への無料公開 | 動的APIを使えない公開先 |
| 進行状態 | D1 / DynamoDB | 署名済みtokenをIndexedDBまたはメモリへ保存 | 進行と取得済partをIndexedDBまたはメモリへ保存 |
| 会話履歴（検索AIを含む） | talkごとのcompact event | talkごとの展開済み表示cache | talkごとのcompact event |
| 別端末での再開 | 同じパスコードで可能 | 非対応 | 非対応 |
| プレイヤーの識別 | ローカル開発画面は4桁、公開環境は8桁のパスコード | 不要 | 不要 |
| プレイヤーごとのサーバーDB書込み | あり | なし（入力ログ有効時を除く） | なし |

`static`は判定もブラウザー内で実行し、ゲームAPIを必要としません。進行・compact履歴をIndexedDBまたはメモリへ保持し、AIは使いません。秘匿する本文等をpartへ分けて後読みします。[サーバーなしで公開する](static.md)に制作・公開・更新の手順を記載しています。

## クライアント保存の設定

`playerMode` は判定場所と進行の管理方式を選びます。プレイヤー画面の保存名と再読み込み後の保持は、別の公開ビルド設定で指定します。

```dotenv
VITE_XSTORYPHONE_STORAGE_PREFIX=author-work-prod
VITE_XSTORYPHONE_CLIENT_STORAGE=persistent
```

| `playerMode` | `VITE_XSTORYPHONE_CLIENT_STORAGE` | 動作 |
|---|---|---|
| `server` | 未指定 / `persistent` | 従来のサーバー進行保存とクライアント保存。prefixを適用可能 |
| `browser` | 未指定 / `persistent` | 従来のIndexedDB保存と小さいUI保存 |
| `browser` | `memory` | 進行・履歴・UI状態をページ内メモリだけに保持 |
| `static` | 未指定 / `persistent` | 進行・compact履歴・取得済partを専用IndexedDBへ保持 |
| `static` | `memory` | 同じ進行をページ内メモリだけに保持 |

staticの進行・履歴はbrowserとは別の保存領域を使います。方式を切り替えた際の自動移行はしません。

`server` と `memory` の組合せ、不明な保存方式、設定値の前後空白などはdev起動・クライアントビルドで拒否します。Viteが実際に解決するshell環境変数と `.env` 等の値を検証します。設定はページ中固定であり、実行中の切替UIや保存失敗時のmemoryへの自動fallbackはありません。

prefixはserver/browser/static共通で、IndexedDB名とlocalStorage/sessionStorageの保存キーすべてに `prefix:従来の名前` の形で付きます。未指定・空文字なら従来の保存名を維持します。他作者と同じoriginを共用するpersistent公開では、作者・作品・配備環境を識別する重複しないprefixを必ず指定してください。通常更新ではprefixと `project.id` を維持します。prefixを変えると別の保存領域になり、旧保存の探索・自動読込・移行・削除はしません。serverの同じパスコードを別プレイヤーにする設定でもありません。

prefixは秘密値ではなく、保存名の誤衝突を防ぐためのものです。同一originの他のコードからのアクセス制御、ブラウザーの容量制限やサイトデータ削除の隔離にはなりません。memoryでは保存先へアクセスしないためprefixは任意です。

### browser/staticのmemory

選択シナリオを `playerMode: "browser"` にしたうえで、次のようにローカルビルドできます。このコマンドはクラウドを変更しません。

```sh
VITE_XSTORYPHONE_CLIENT_STORAGE=memory npm run build:aws
```

memoryはエンジン管理の進行token、入力、会話・検索履歴、表示cache、開始前確認、ロック、既読などをJavaScript変数とMapだけに保持します。Cookie、localStorage、sessionStorage、IndexedDBへゲーム保存せず、既存保存の読込・削除や利用可否確認も行いません。persistentの保存があっても新規開始し、memory中の進行をそこへ同期しません。persistentへ戻せば元の保存領域を再び使います。

同じページ内のアプリ移動、通常の戻る・進む、非表示からの復帰では保持します。各ページは独立したプレイであり、一方のreset/logoutは他方へ影響しません。通常のreload、新規タブ、ページ破棄後の再生成、閉じたタブの通常の再オープンでは最初からです。BFCacheでJavaScript実体ごと復帰した場合は続くことがあります。モバイルOS等によるタブ破棄でも進行を失うため、中断再開を前提とする作品には不向きです。

memoryではclientRevision不一致を `AP-UPDATE` として停止し、自動reloadしません。通常の通信エラーの限定再試行は維持しますが、手動reloadや致命エラーからのreloadでは最初からになります。復旧用tokenを別の保存先へ退避する処理はありません。

GA4はmeasurement IDが設定済みでも読み込みません。browserのゲームAPIへの開始・操作・固定PIN検証は `credentials: "omit"` と `cache: "no-store"` を使い、状態JSON応答にも `Cache-Control: no-store` を付けます。browserの判定・署名・hookはbackendで実行します。staticはAPIを使わず、必要な定義ファイルを同じ取得設定で読みます。どちらもmemoryが通信不要を意味するわけではありません。

この保証はエンジン管理のプレイデータについてです。ホストや埋め込みページ、作者が追加した任意JavaScriptによるCookie・保存、HTML・画像・音声・iframeの通信、静的ファイルの通常HTTP cache、ブラウザー標準のURL履歴やOSの管理までは禁止しません。History APIには画面詳細を復元できないページ内識別子だけを渡します。`PLAYER_INPUT_LOGGING`、外部hookの副作用、APIアクセスログは別の設定・責務であり、「サーバーを含め何も記録しない」設定ではありません。

## serverモードのアクセスコード

公開環境のserverモードは8桁のプレイヤーパスコードを使います。既定では任意の8桁を受理しますが、`ACCESS_CODE_SECRET` を設定すると、発行済みコードだけを受理する人数限定運用へ切り替わります。

```sh
ACCESS_CODE_SECRET='十分に長い秘密値' npm run access-code -- 0001
```

複数件をまとめて発行する場合は開始連番と件数を指定します。

```sh
ACCESS_CODE_SECRET='十分に長い秘密値' npm run access-code -- --from 0001 --count 100
```

引数はプレイヤーを識別する4桁の連番で、コマンドは秘密値から求めた4桁のチェック値を前へ付けた8桁を表示します。Cloudflare版とAWS版は同じ生成規則を使いますが、両方へデプロイした場合のプレイデータは各データベースへ別々に保存されます。秘密値はコード生成とサーバー判定だけに使い、クライアントへ渡しません。

同じ連番に対する失敗が15分以内に20回続くと、一時的に入力を拒否します。成功時はその連番の失敗記録を消します。これは発行人数と無制限な試行を抑えるための軽い入場制御であり、個人情報を守るアカウント認証ではありません。localhost上のdevelopment・stagingでは従来どおり4桁または8桁の任意コードを使えるため、テスト用コードの発行は不要です。

## プレイヤーパスコードとロック画面

`project_constants` シートの `device.lock_method` で、疑似端末のロック方式を選びます。固定PINならvalueを `fixed-pin` とし、別行 `device.lock_pin` のvalueへ `0420` のような文字列を指定します。PIN行のexposureは必ず `private` にします。Sheetsで先頭のゼロを失わないよう、PINセルはプレーンテキストにしてください。

| `method` | 動作 |
|---|---|
| `player-passcode` | serverモードのプレイヤーパスコードを、端末のロック画面で入力する |
| `fixed-pin` | 作品で設定した共通PINを、端末のロック画面で入力する |
| `none` | ロック画面を表示しない |

`player-passcode` はserverモード専用です。browser/staticモードで指定するとシナリオ検証が失敗します。

serverモードで `fixed-pin` または `none` を選んだ場合も、プレイヤーを識別して続きを読み込むためのパスコードは必要です。このパスコードは開始前確認のあと、疑似端末を表示する前の画面で入力します。その後、`fixed-pin` なら端末のロック画面、`none` ならホーム画面へ進みます。

`fixed-pin` では、プレイヤーパスコードをブラウザーのメモリに一時保持し、固定PINも正解した時点で初めてプレイデータを読み込みます。固定PIN画面で止まっている間に、`session_started` hookや予約イベントが進み始めることはありません。ページをリロードした場合は、プレイヤーパスコード画面へ戻ります。

| 保存モード | `method` | 開始時の流れ |
|---|---|---|
| `server` | `player-passcode` | 開始前確認 → ロック画面でプレイヤーパスコード → ホーム |
| `server` | `fixed-pin` | 開始前確認 → 端末外でプレイヤーパスコード → ロック画面で固定PIN → ホーム |
| `server` | `none` | 開始前確認 → 端末外でプレイヤーパスコード → ホーム |
| `browser` | `fixed-pin` | 開始前確認 → ロック画面で固定PIN → ホーム |
| `browser` | `none` | 開始前確認 → ホーム |
| `static` | `fixed-pin` | 開始前確認 → ロック画面で固定PIN → 必要part取得 → ホーム |
| `static` | `none` | 開始前確認 → ホーム |

固定PINは4桁から8桁の数字文字列で指定し、`0420` のような先頭のゼロも保持します。正解値はクライアント用データへ生成しません。server/browserはサーバーで、staticは部分hashと回答JSONの取得で判定します。正解なら画面を進め、不一致ならロック画面にエラーを表示します。DBへ試行履歴やロック状態は保存しません。追加partを取得する`device.unlock_load_part`の指定は[staticとpartの説明](static.md)を参照してください。

固定PINは、ゲームとしてPINをクライアントへ露出させずに入力させるための機能です。アカウント認証、課金状態、個人情報などを守る強いセキュリティ機能ではありません。短い共通PINには総当たり耐性がなく、公開repositoryのシナリオ原本に書けばrepositoryの閲覧者には分かります。この割り切りを超える保護が必要な作品では、固定PINへ認証機能を継ぎ足さず、アクセス方式そのものを別途設計してください。

## テストプレイのリセット

browser/staticはビルド時の`VITE_XSTORYPHONE_RESET_FOR_TESTING=true`（dev起動では既定で有効）でテスト用リセットを有効にします。進行はローカル保存から消去し、リセット用APIへ通信しません。以下のAPI側の環境制限はserver向けです。

`/reset-for-testing` を開くと、現在のプレイヤー進行を初期状態へ戻せます。この操作は `APP_ENV` が `dev` / `development` / `stg` / `staging` の環境と、環境名未設定のlocalhostだけで利用できます。dev・stgのデプロイスクリプトはクライアント側の `VITE_XSTORYPHONE_RESET_FOR_TESTING` も自動で有効にします。`prod` / `production` ではURLを解釈せず、APIを直接呼んでも `404` になり、プレイヤー自身が有料体験を繰り返す入口にはなりません。

dev・stgでは通知シェードに「最初から」を表示します。URLと同じ消去処理で、開始前確認へ戻ります。リセット自体では初期会話・開始hook・初期予約を実行せず、必要なパスコード／PINを入力した次の通常開始で準備します。prodでは「最初から」を表示しません。ロック画面を使う作品では通常のロック操作だけを表示し、`method: "none"` ならその操作も表示しません。

serverではプレイヤーIDと入力・監修記録を維持し、進行・会話履歴・予約・生成音声job・hook LLM cacheを消去します。そのプレイヤーの既存sessionはすべて失効するので、他のタブや端末も再認証が必要です。DynamoDBの消去が中断された場合は、リセットの再試行または同じパスコードでの開始時に残りを消去します。初回の開始hookが失敗した場合も、未初期化の進行を維持して次の開始で再試行します。

テスト用リセットに失敗して進行を再開できない場合は、`/reset-for-testing` を開き直してリセットを再実行してください。

本番で特定プレイヤーの再プレイを許可する場合は、公開リセット機能を有効にせず、新しいパスコードの発行など運営側で対象を限定できる方法を使ってください。

## サポート用のログアウトとローカル初期化

公開URLの末尾へ `/logout` を付けて開くと、現在のブラウザーに保存した認証・表示状態を解除できます。通常のゲーム画面には表示しない、運営が必要な場合だけ案内するサポート用の入口です。保存モードにより、進行への影響が異なります。

| 保存モード | `/logout` の動作 |
|---|---|
| `server` | 選択中prefixのブラウザーのsession tokenと端末内の表示状態を破棄する。DBのプレイヤー進行と会話履歴は残り、同じパスコードで再開できる |
| `browser` + `persistent` | 選択中prefix・当該 `project.id` のローカル進行token、会話履歴、端末内の表示状態を削除し、最初からになる。他のprefix・projectの進行保存は削除しない |
| `browser` + `memory` | ページ内の進行・表示状態を破棄して開始画面へ戻る。永続保存には触れず、保存データの削除確認も表示しない |
| `static` | browserと同じ確認方針で、static専用の保存だけを初期化する。persistentでは当該prefix・projectの進行、compact履歴、取得済partが削除される |

browser + persistentの本番環境では、削除内容を表示し、プレイヤーが明示確認した場合だけ初期化します。取り消した場合は保存を維持します。テスト用リセットが有効なdev・stgでは、明示的に `/logout` を開いた際の確認は省略します。これは認証エラーによる自動削除とは別の操作です。起動時の保存検査でゲーム画面を表示できない場合も、同じ入口を使えます。他のタブが保存を開いていて初期化を完了できない場合は、その作品の他のタブを閉じてからリロードしてください。実行済みの削除要求は取り消せず、他のタブを閉じた後に完了する場合があります。

persistentの起動時の保存検査の `corrupt` は、現在の実装で保存を読み取れないことを示し、復旧不能と確定した意味ではありません。修正版の配信を待つ、リロードする、といった選択を残し、保存の削除は進行を失っても初期化することに同意した場合の最終手段としてください。通常の通信障害、容量不足、別タブとの競合、API応答の不整合では、初期化を案内しないでください。

## browserモードの署名

`browser` では `BROWSER_STATE_SECRET` をHMAC署名に使います。この値はクライアントへ渡しません。localhost以外で未設定の場合は新しいプレイを開始できません。

公開後は環境ごとに同じ `BROWSER_STATE_SECRET` を維持してください。通常のデプロイやシナリオ更新で変更すると、保持中のtokenを検証できなくなります。browserのplayer APIが401を返した場合は、dev・stgを含む全環境で状態を保持し、開始前へ戻さず `AP-BROWSER-STATE` を表示します。署名鍵を誤変更した場合は元の値へ戻してください。persistentではリロードして再開できますが、memoryではリロードすると進行を失います。このエラーを理由に `/logout` やサイトデータの削除を案内しないでください。

tokenは改ざんを検出しますが、暗号化はしていません。進行JSONをgzip圧縮してから署名します。圧縮は秘匿ではなく、内容は展開すれば読めます。中に入る状態変数は、シナリオで宣言した既定値と異なる値だけです。進行フラグは利用するまで既定値のままにすると、未到達の将来状態をtokenへ増やさずに済みます。既定値と「未設定」を区別したい場合だけ、別の明示的な状態変数を用意してください。

同じ `project.id` のシナリオ更新では、保存済み状態を現在の定義へ読み替え、次の応答から新しいrevisionのtokenへ更新します。通常のシナリオ更新で `project.id` を変更しないでください。公開後は、進行中に参照されるapp・content・talk・blockのIDも安易に変更しないでください。プレイヤーが到達済みのblockは本文を修正できますが、block内のmessage件数と順序は変えないでください。破壊的なID変更や履歴配置変更の自動移行は行いません。

browserモードのplayer APIは、操作内容とtokenを同じJSON bodyで送ります。serverモードとの違いは共通のrequest境界で吸収し、状態復元後の判定・hook・状態遷移は同じ処理を使います。

browser + persistentでは、署名token、最新の公開PlayerState、今回変更されたtalk streamを、一つのIndexedDB transactionでまとめて保存します。transactionが完了するまで新しい状態を画面へ適用しないため、tokenだけ進み履歴だけ古い状態になることを防ぎます。メッセージ、チャット、固定の`search_agent`を同じtalk単位で扱い、各talkを一recordとします。message単位の細分化やindexは行いません。memoryでも同じ親token・stateVersion・履歴seqの検証を行い、候補全体が正しい場合だけページ内の状態を一括で置き換えます。

browser + persistentでlocalStorageへ残すのは、ロック状態、最後に開いた内容、既読cursor、開始前確認など、失われてもゲーム進行を変えない小さいUI状態だけです。browser進行tokenやPlayerStateの複製は保存しません。

tokenには、異常な状態肥大を早期に検出するため64KBのアプリ上限があります。これは作品のルーム数やコンテンツ数を通常規模へ制限する値ではありません。通常の進行状態は圧縮によりこれより十分小さくなります。それでも大量の到達済みIDや状態値で上限へ近づく場合は、状態の持ち方かserverモードの利用を検討してください。
上限を超えた場合は、ユーザーサポートで原因を切り分けられるように、画面へエラーコード `AP-PROGRESS-SIZE` を表示します。

会話履歴は署名対象にせず、talk stream内の連番で差分を追加します。履歴を書き換えても、コンテンツ修復、添付解錠、メッセージ内リンクの利用可否は変わりません。これらの判定には、署名された小さい到達済み状態だけを使います。検索AIも独立した履歴ではなく固定の`search_agent` talkです。繰り返し検索で保存量が増え続けないよう、このtalkだけは入力・発話・検索結果カードを合わせた直近200表示項目に保ちます。

serverモードの会話履歴は、プレイヤー入力本文と、シナリオ発話のblock ID・参照template値・表示時刻をcompact eventとして保存します。D1のメッセージ／チャットはevent行、直近200項目へ入れ替える検索AIは既存の`player_transcripts` 1行、DynamoDBはtalk単位itemという各DBに自然な物理配置を使いますが、論理eventは共通です。browserモードでは、未到達台本をclientへ渡さない境界を守るため、backendが展開した到達済みmessageをローカル表示cacheへ保存します。いずれも履歴本文を進行認可には使いません。

通常会話の記録時刻は、同じ会話の前の出力より後になるように保存します。短時間に続けて入力したり実時計が戻ったりしても、履歴を再取得した際の順番が変わらないためです。表示時刻は厳密な実時間の記録ではなく、連続した返答ではわずかに先へ進むことがあります。

## 未到達情報の扱い

以下はAPIを利用するserver/browserの境界です。staticでは未取得partを秘匿境界とし、配布済part内の未表示内容は解析できます。秘匿する続きは[partへ分けて配置](static.md)してください。

初期クライアントデータとAPIは、未到達の本文、画像URL、ヒント、会話を返しません。`repairable` の未修復コンテンツは、壊れた表示に必要なIDと代替表示だけを返します。`hidden` の未到達コンテンツは存在自体を返しません。

保護対象の画像や音声を `public/` へ置くことはできます。ファイル名は作者が推測されにくい名前にしてください。URLへ到達したプレイヤーが共有し、第三者が直接取得できることは許容する設計です。ファイル名の自動変更や強度検査は行いません。

予定イベントもtokenへ入るため、`context.schedule.after` の `fields` へ未到達本文や答えを書かないでください。イベントIDはクライアント向けの不透明IDへ変換されます。

## 割り切り

`browser` + `persistent` はIndexedDBを含むサイトデータを消すと最初からになります。複数端末の引継ぎ、複数タブの完全同期、過去の正しいtokenを意図的に再利用する操作は保証しません。同じタブからのAPI操作は順番に送信します。同じprefix・projectの別タブが先に進行を保存したことを検出した場合は、古い画面から操作を自動適用せず、エラー画面からリロードして先行状態を読み直します。memoryの各ページは保存を共有せず、リロードで最初からになります。

IndexedDBが無効な環境へlocalStorage版の保存処理をfallbackとして重ねることはしません。二つの正本が分岐することを避けるためです。SafariのLockdown ModeなどIndexedDBを利用できない環境ではbrowser + persistentを開始できません。Private Browsingではpersistentの保存が一時的になり、終了時に消える場合があります。通常環境でもquota、端末の空き容量、ブラウザーのstorage eviction、ユーザーによる削除を超えた永続性は保証しません。保存に失敗した操作は成功扱いにせず、`AP-STORAGE`を表示します。memoryは明示的に選ぶ別の保持方針であり、このエラーから自動切替しません。

persistentのIndexedDB保存では、すべてのtalk履歴を毎回同期的に読み書きする処理は避けられます。ただし、公開PlayerStateは操作ごとに保存し、変更された一つのtalkはそのtalk全体を書き戻します。起動時は保存済みstreamを読み、画面用の全messageをメモリへ構成するため、履歴量にかかわらず一定時間で動くことまでは保証しません。

LLM会話も利用できますが、応答を受け取る直前に通信が切れた場合の完全な一回実行は保証しません。無料公開版では、再現性と費用の面から正規表現分岐を中心にすることを推奨します。

`PLAYER_INPUT_LOGGING` は両モードで既定では無効です。有効にすると、`browser` でも検索・会話入力だけは監修用DBへ記録されます。大規模な無料公開で有効にする場合は、保存量と費用を先に見積もってください。
