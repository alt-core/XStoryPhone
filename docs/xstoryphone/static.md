# サーバーなしで公開する

`project_constants`の`player.mode`を`static`にすると、ゲームAPIを使わず、静的ファイルだけでプレイできます。判定・検索・hook・修復・履歴の処理はserver/browserと共通です。進行とcompactな会話eventはIndexedDBへ保存し、`memory`を選ぶ場合はページ内だけで保持します。

従来の`browser`は、保存先がブラウザーでも判定にAPIを使います。また、`build:static`というコマンド名だけでは実行モードは変わりません。実行方式はSheetsの`player.mode`で選びます。

## 制作とビルド

1. 全シナリオ表は引き続きGoogle Sheetsで制作します。`player.mode=static`にし、AIを使う分岐・抽出・hookは使用しません。
2. `#part名`で、正解後まで配布しない本文・素材・hookを分けます。
3. 初回だけ、選択した作品の秘密の取得先を初期化します。

```sh
XSTORYPHONE_SCENARIO_DIR=scenario/my-story npm run scenario:static:init
XSTORYPHONE_SCENARIO_DIR=scenario/my-story npm run build:static -- --base=/games/my-story/
```

`dist/static/`の中身だけを公開先の指定サブパスへアップロードします。ゲームAPI、AWS/Cloudflareの設定、APIキーは不要です。`VITE_XSTORYPHONE_API_BASE_URL`は指定しません。HTTPSで公開し、ローカル確認ではHTTPの静的サーバーを使ってください。`file://`で直接開く構成ではありません。

`.secrets/static-parts.json`は非公開の取得先対応表です。Gitや公開先へ入れず、作者間で安全に共有・バックアップしてください。通常ビルドは既存の取得先を維持し、新しいpartだけを追加します。紛失時に自動で別の取得先を生成し直さず停止します。

共有ドメインでの公開は重複しない`VITE_XSTORYPHONE_STORAGE_PREFIX`を使います。保存不要なら`VITE_XSTORYPHONE_CLIENT_STORAGE=memory`を指定できます。memoryの各タブは独立し、リロードで最初からになります。[保存設定](player-modes.md)も確認してください。

## partの所属

各TSVのA列`comment`へ、他セルを空にして次のように記述します。

```text
#base
…初期取得する定義…
#evidence
…正解後に取得する定義…
```

最初の宣言を省略した区間は`base`です。名前は他のIDと同様、英小文字で始まる英小文字・数字・`_`・`-`を使います。同じpartを複数区間で宣言できます。part境界で空欄継承を切るため、talk/from等を改めて指定してください。`talk_blocks`も境界の後で`*talk_id`とblock名を指定します。

`talk_flow`は分岐、`talk_blocks`は本文の所属をそれぞれ指定します。同じtalkへ後のpartから分岐や本文を追加できます。block IDへpart名を付ける必要はありません。メモ・画像・添付・人物・状態変数・hook等にも同じ宣言を使います。`project_constants`と起動時の`schedules`だけはbase専用です。

取得済partは増える一方です。取得だけで修復したり、会話地点を戻したり、初期値を上書きしたりはしません。`requires`・暗黙ロード・`unload`はありません。

`npm run scenario:talk-flow:writer-review`は、partごとの定義IDと取得入口、追加取得なしのpasswordも一覧します。作者向けの非公開資料なので、生成レポートを静的ホスティングへアップロードしないでください。別partのattachmentsを参照するメモ・画像・着信等は、URLを先行配布せず取得後に結合します。その素材を表示する時点までに、必要なpartを明示的に取得してください。

制作時には取得入口ごとに、確実に利用できる定義を検査します。開始時点で必ず必要な素材の不足はエラーにし、前の操作で取得している可能性がある参照は警告に留めます。警告は「その参照が不正」という断定ではなく、作者による経路確認が必要という意味です。実行時にも必要な定義を確認し、未取得の本文を空表示で済ませません。

`talk_flow`に対応するfrom行がないblockは、[全モード共通の読み取り専用終点](conversation.md#tsvの列)にできます。一方、そのfrom行が後のpartにある場合は、入力地点の定義不足として検査します。終点のためだけに入力をdisableする行を追加する必要はありません。

## 正解による取得

会話は`type=secret`にし、`text`へJSON文字列形式の候補をセル内改行で列挙します。

```text
"月明かり"
"つきあかり"
```

`next`は次のように書きます。

```text
/load evidence
answer_reply
```

`/load`はsecretのnextの先頭だけで使えます。複数partは一行ずつ指定します。取得と検証が終わってからset・発話・hookを処理するため、未取得の本文を空の返信として成功させません。

passwordも同じ候補形式です。`passwords.load_part`に取得するpart名を記述します。複数指定はセル内改行です。空欄は「追加取得なし」という正式な指定で、baseへ本文を含めた解錠演出も許可します。ただし、既取得でも明示取得先でもないpartの本文を解錠することはできません。

passwordの入口自体も任意のpartへ置けます。例えば入口がevidence、解錠する添付本文がvaultなら、evidence取得時に鍵付き添付の枠を用意し、password正解後にvaultを読みます。本文・素材URLを枠へ先行配布することはありません。

固定PINの取得先は`device.unlock_load_part`です。空欄・未指定は追加なし、複数指定はセル内改行です。PINの4〜8桁・先頭ゼロ・数字の一致判定は変えません。passwordとsecretの語句はNFKC・前後trim・小文字化を共通に使いますが、PINにはこの正規化を適用しません。

## 初期の破損枠とhook

repairableなコンテンツは、本文を後のpartへ置いても最初から破損枠を表示できます。初期の破損会話は件数・順序・seq・template参照キーだけを先行させ、必要なenvをtalk初期化時に保存します。修復時の値で初期envを取り直しません。初期表示に必要な条件変数はbase、開始時の履歴envに必要な変数は開始時に取得できるpartへ置きます。

hookは所属partの取得後に有効になり、原本の行順で実行します。`cond`は各scriptの直前に、先行scriptの状態更新を反映して一度だけ判定します。一つだけphaseを進めたい場合は、一つの分岐またはscript内のif/elseで記述してください。

`event=part_loaded`、`target=part名`で、初回取得時の案内等を追加できます。

```text
必要partの取得 → 通常のset・出力 → part_loaded → 通常の完了hook → 一括保存
```

baseも新規開始時だけ、`session_started`より先に通知します。再開・再認証・再取得・通常更新で重ねて呼びません。複数partは取得宣言順で通知し、各partのhookは原本順に実行します。`part_loaded`で終端のeffectSequenceは開始できません。必要なら通常の完了hookへ置いてください。通常のeffect、状態変更、会話追加、予約は利用できます。

## 隠せる範囲と限界

- 正答原文と継続処理を初期配布せず、入力から導出した取得先で回答JSONを読みます。一部のhashを先行配布し、通常の誤答では未知URLへアクセスしません。
- 正解フラグだけを変更しても、未知の取得先は得られません。一方、総当たり・辞書攻撃、取得済み情報の共有は防ぎません。短い数字等を強い秘密として扱わないでください。
- baseや取得済partへ含めたものは解析できます。cond・hidden・repairable・password表示だけでは、配布済データを秘匿できません。
- 素材のURLは作者が推測されにくい名前にします。公開ファイル一覧や全ファイルZIPを誰でも取得できるホストでは、この秘匿方式は成立しません。
- 作者の任意HTMLやStageへ書いた秘密・計算したURLを完全に検出する保証はありません。ビルド監査と、実際の配布物の確認を併用してください。

現在はPBKDF2-SHA-256を10万回使い、操作内の同じ入力は重い導出を共有します。照合用prefixは64bitです。secret/password照合へ到達した時だけ計算し、通常のmatchの前には計算しません。端末ごとの待ち時間は作品の公開前に確認してください。

## 再開・更新・失敗時

保存は進行・変更履歴・取得済partを一つのtransactionで確定します。操作前に期限到来の予約を確定した後、ユーザー操作が拒否された場合は、予約の確定だけを維持します。別タブが先に進めた場合は自動マージせず、エラーとリロードで再開します。保存失敗でmemoryへ切り替えたり、既存進行を削除したりはしません。

通常更新ではproject ID・partの取得先・block ID・初期履歴配置を維持してください。新しい配布版から取得済partを揃えて再開し、revision変更だけで全員を初期化しません。公開時は新ファイルを先に、入口HTMLと`static-entry.json`を最後に更新し、プレイ中の旧ページが必要とする`scenario/<配布版>/`をすぐ削除しないでください。新しい秘密を取得済partへ追加しても、以前の取得者には秘密になりません。

ファイル取得の通信障害・429・5xxは、操作全体で最大2回再試行します。正答後の403/404、不正JSON、配布版不一致を誤答として続行しません。設定・配信を直した後にリロードします。memoryではリロードで進行を失います。

JSON本文の読取りとhook moduleも同じ再試行予算を使います。moduleはブラウザーからHTTP状態を区別できないため、構文エラー等の明確な不正以外は予算内だけ再試行します。失敗したimportを記憶するブラウザーに対応するため、再試行時だけURLへ回数を付けます。eval・サービスワーカー・無制限の再試行は使いません。

音声・字幕・動画は既存UIを使います。外部生成音声には各コンテンツの固定audioを代替として指定し、代替のない参照はビルドで拒否します。ページが閉じている間に予約は動かず、再開時に期限到来分を処理します。

作品独自のStage・アプリ・HTMLに書かれた外部通信は、自動的に静的化しません。エンジンの標準機能とは別に確認してください。

監修では取得済partを指定して分岐を試せます。監修API・ログ・作者用データはstatic成果物へ配布しません。試行は分岐・抽出・set・出力の確認であり、part_loadedを含むhook全体は実プレイで確認してください。

ローカル監修は既存の`npm run db:migrate:local`、`npm run dev`を使います。devでは作者向けのローカルWorkerも起動しますが、staticのプレイヤー操作はAPIを使いません。公開確認は`build:static`の成果物をAPIのない静的サーバーへ置いて行います。TSVを更新した後は再ビルドまたはdevを再起動してください。
